# PR 自动审核与测试系统 · 总体实施方案

> 状态:阶段 1-2 已实施(pr 缓存/轮询/状态展示、AI 评估管线);阶段 3-4 未实施
> 目标:将本项目从"人工操作控制台"演进为"常驻服务 + AI 预审 + 自动测试"的主动审核系统

## 1. 目标形态

- 服务常驻运行,定时轮询所有项目的开放 PR,增量同步到 SQLite 缓存
- 检测到新 PR(或 head SHA 变化)时,调用大模型评估该变更是否需要运行测试
- 判定需要时,自动通过 SSH 到测试服务器指定目录运行测试命令
- Web 界面可见每个 PR 的自动化状态(AI 结论、测试状态、日志),支持手动发起测试

## 2. 核心设计原则

1. **状态机驱动**:PR 的自动化状态是数据库中的显式字段,而非每次推断
2. **SHA 变更检测**:以 head SHA 为变更依据,同 SHA 的 AI 评估结果直接复用,不重复调用模型
3. **确定性规则优先**:`.sql` 变更等硬规则直接判定需要测试,AI 只处理模糊场景
4. **人审兜底**:AI 与测试通过后停在"待人工确认",合并动作保留人工触发
5. **增量演進**:四个阶段独立交付,每阶段结束系统都可用、可回退

## 3. 模块划分

```
server/
  main.ts        # HTTP 服务 + 静态文件 + 路由注册
  db.ts          # SQLite 初始化、迁移
  poller.ts      # 定时轮询、增量同步、变更检测        [阶段1]
  ai.ts          # LLM 评估(结构化输出、提示词模板)    [阶段2]
  tester.ts      # 测试执行管线(锁、超时、日志)        [阶段3]
  routes/        # API 路由(projects/pulls/deploy/...)
```

前端在现有页面扩展:PR 列表加自动化状态列与筛选,详情区展示 AI 结论与测试状态。

## 4. PR 自动化状态机

```
new ──→ ai_reviewing ──┬─→ no_test_needed ──→ (等待人工)
                       └─→ needs_test ──→ testing ──┬─→ test_passed ──→ (等待人工确认合并)
                                                    └─→ test_failed ──→ (等待人工/重测)
任意状态 ──→ merged / closed(轮询发现 PR 关闭)
head SHA 变化 ──→ 回到 new(重新评估)
```

## 5. 阶段划分

| 阶段 | 内容 | 交付物 |
| --- | --- | --- |
| 1 | PR 缓存 + 轮询 + Web 状态展示 | **已实施**:pr_cache/sync_state 表、poller 轮询(重入保护/项目隔离/开关)、缓存读接口、状态徽章、设置页自动化区块 |
| 2 | AI 评估管线 | **已实施**:ai.ts(OpenAI 兼容调用/提示词模板/输入截断)、evaluatePending(硬规则/重试降级/同 SHA 去重)、AI 结论条与设置页配置 |
| 3 | 测试执行管线 | test_configs 配置(本地/SSH、位置模板、命令、AI 决定)、自动+手动执行、日志与状态回写,详见 [phase-3-design.md](./phase-3-design.md) |
| 4 | 通知、审计与打磨 | 服务端 webhook 通知(钉钉/企微)、AI 决策审计表、全局/项目级自动化开关 |

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| Gitee API 限流 | 增量拉取(updated_at 过滤)+ 项目级间隔可配 + 请求失败退避 |
| LLM 输出不稳定 | 强制 JSON Schema 输出,解析失败重试 1-2 次后降级为 needs_test(宁多测不漏测) |
| 测试命令挂死 | 执行超时强制 kill;同项目并发锁;全局并发上限 |
| 调试期间疯狂调 API | 全局自动化开关(阶段4,但阶段2先做全局配置项) |
| 误触发合并 | 设计上 AI/测试通过≠合并,合并仅人工触发 |
